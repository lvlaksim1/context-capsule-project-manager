# Context Capsule v2 — Portable Project Manager Model

Status: development design implemented on `v2-manager-runtime`.

## Product definition

Context Capsule v2 is not merely repository-local project memory. It is a portable durable representation of a Project Manager that can be reinstantiated in a new chat, model, process, or agent runtime.

A runtime is an execution carrier. The manager remains the same manager while runtime instances change.

## Manager state model

The active manager state is deliberately separated into:

- **Beliefs** — current factual/inferential model of the project, with provenance and authority.
- **Goals** — desired durable outcomes.
- **Intentions** — accepted commitments that survive runtime replacement.
- **Plans** — current strategy for satisfying intentions.

This is inspired by BDI agent architecture but adapted for repository-native engineering/project management.

## Project Manager Contract

Every v2 installation carries a Core-managed `.context/manager/CONTRACT.md`. The Contract is the normative behavioral boundary for the persistent Project Manager. The universal Protocol operationalizes that Contract; the project-specific mandate narrows authority for one project.

The Contract covers owner-message semantics, bounded authority, BDI state, commitment lifecycle, evidence revision, reconciliation, durable-memory lifecycle, self-modification, external expertise, and persistence/privacy.

## Universal Manager Protocol

Universal professional behavior belongs to Core and is installed as `.context/manager/PROTOCOL.md`. Project-specific authority belongs to `.context/manager/mandate.md`.

The universal loop is:

`Reinstate → Reconcile → Plan → Execute → Verify → Reflect → Persist`

## Stable identity

`.context/manager/identity.json` carries a stable `manager_id`. `manager_id` is repository-scoped and must not be replaced by chat IDs, model names, process IDs, or other runtime identifiers.

## Authority coordinates

v2 separates repository product authority from Project Manager state authority.

- `authority.manager_state_branch` is the durable locus of manager identity, mandate, BDI state, memory, and working views.
- `authority.product_branch` is the default live product baseline used when reconciling repository facts.
- `authoritative_branch` remains only as a compatibility alias of `authority.manager_state_branch`.
- `discovery_branch` remains a bootstrap/discovery location and does not itself imply either kind of authority.

For a normal repository both authority branches are commonly `main`. For a permanent context branch, manager state can live on `context` while the product baseline is `main`. For Context Capsule v2 development, manager state lives on `v2-manager-runtime` while the production baseline remains `main`.

Execution on a feature branch never promotes that branch to either authority automatically.

## Typed memory

- semantic memory — reusable knowledge and verified lessons;
- episodic memory — selected significant situations where chronology/context matters;
- procedural memory — learned workflows and verification techniques.

Decisions and rules remain first-class durable project surfaces.

## Provenance and memory poisoning boundary

Manager beliefs must preserve source and authority. External content, specialist-agent output, and manager inference are not automatically authoritative. Conflicts remain explicit until resolved; supersession is explicit rather than silent.

## Evidence revision semantics

Every new evidence item is interpreted relative to an existing proposition as one of:

- **confirming evidence** — supports the same semantic state; no write-back is required solely because the evidence is newer;
- **superseding evidence** — changes the accepted value/truth after authority adjudication; the previous record remains auditable as superseded;
- **conflicting evidence** — incompatible evidence without sufficient authority to resolve; both sides remain explicit.

Freshness is metadata, not a semantic revision operator. In particular, a later successful CI run that confirms the same verified state must not force another capsule commit simply to record the latest run number. This prevents self-generated verification/write-back loops.

## Authoritative state vs working views

The Project Manager's BDI state and newer verified live evidence are authoritative. `current/state.md`, `current/blockers.md`, `current/next.md`, and `handoffs/latest.md` are working views for compact recovery and human inspection.

A conflict in a working view does not create a second source of truth. Reinstantiation must surface the discrepancy, prefer higher-authority manager/live evidence, and repair the stale view. Semantic write-back that changes shared working meaning must update all affected views together.

## Coherent manager-state generations

Semantically coupled Project Manager state is sealed by `.context/manager/state-integrity.json`. The marker records a monotonically advancing generation and Git blob content identifiers for manager beliefs/goals/intentions/plans plus `current/state.md`, `current/blockers.md`, `current/next.md`, and `handoffs/latest.md`.

For protected v2 capsules, `READY` and `recover` fail closed when the marker is missing, malformed, or disagrees with any coupled file. This turns interrupted multi-file publication into an explicit NOT READY state instead of allowing a replacement runtime to consume a mixed checkpoint.

The preferred publication is one atomic Git commit containing all semantically coupled changes plus the new marker. Where a transport cannot do that, it may publish intermediate file commits only while retaining the previous marker; the final marker update seals the new generation. Consequential reinstantiation is blocked throughout the intermediate window.

Existing v2 capsules without this marker are legacy-unsealed. They are not silently reinterpreted as protected; explicit `repair` bootstraps generation 1. A capsule that already declares coherence protection but has a mismatching marker is not auto-sealed by `repair`; semantic reconciliation is required first.

## Bounded recovery invariant

Recovery budgeting may reduce secondary context, but it must not degrade manager identity or active responsibility. Manager protocol, identity, mandate, project authority context, active beliefs/goals/intentions/plans, and active rules are mandatory. If they do not fit, recovery fails explicitly rather than silently producing an incomplete Project Manager. Working views and deeper memory can be omitted and indexed for on-demand retrieval.

## Runtime checkpoint boundary

Context Capsule is not a workflow/checkpoint engine. Conversation history, pending tool calls, hidden reasoning, and transient executor state are runtime state. A runtime may persist its own checkpoint separately. `runtime.checkpoint_is_capsule_state` is permanently `false`.

## Handoff

`handoffs/latest.md` remains available as an emergency/convenience summary. It is no longer a required continuity primitive for `READY`; the manager's durable identity and active state are authoritative.

## Lifecycle

- `install`: creates a v2 structural capsule; initially VALID but normally not READY until manager/project semantics are captured.
- `upgrade`: explicit v1.3.x → v2 transition. It preserves project-owned context and adds manager/memory surfaces. Major upgrade is never hidden inside repair.
- `repair`: operates only within the already-installed v2 major line.
- `ready`: means Project Manager reinstantiation readiness.
- `recover`: emits a deterministic manager reinstantiation pack.

## Compatibility invariant

Stable v1.3.1 remains a valid released product. v2 development must not mutate known consumer repositories or silently upgrade them.

## Authority-bearing lifecycle integrity

Authority-bearing `validate`, `ready`, and `recover` bind every Core-managed governing surface
(`.context/ENTRYPOINT.md`, project protocol, Manager Contract, and Manager Protocol) to the exact
Git objects under the declared `.context/capsule.json.core_commit`. A SHA-shaped value alone is
insufficient. The declared commit must be present in the local Core Git object database and the
installed governing content must exactly match that commit's canonical templates.

Normal `ready` and `recover` are valid only from the checkout identified by
`authority.manager_state_branch`. `--expected-manager-ref` can additionally pin an exact commit.
Divergent, detached, exported, or feature-branch snapshots require explicit `--non-authoritative`
maintenance/audit mode; that mode never emits a Project Manager reinstantiation claim and its
recovery pack explicitly forbids resuming the manager from that evidence snapshot.

Decision-relevant beliefs and durable semantic/procedural memory are checked entry-by-entry for both
`source:` and `authority:` before READY. Provenance on one entry can never satisfy another entry.

Mutable Core SHA is canonical only in `.context/capsule.json.core_commit`; working views must refer
to that field rather than copying the value.
